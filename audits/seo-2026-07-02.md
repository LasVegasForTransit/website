## Findings

### High - Missing paths return 200 homepage responses

Evidence:

- `https://lasvegasfortransit.org/totally-missing-seo-audit-test/` returned 200, title `The transit movement Vegas needs - Las Vegans for Better Transit`, canonical `https://lasvegasfortransit.org/`.
- `https://lasvegasfortransit.org/nonprofit-preview/` returned the same 200 homepage response.
- `https://lasvegasfortransit.org/brand/` and `/colophon/` also returned homepage responses on production, while the current local checkout has untracked route files for both.

Why it matters:

Search engines can treat this as a soft-404 pattern and may waste crawl budget or index duplicate homepage URLs. It also hides broken inbound links because any typo looks like a valid page.

Recommended fix:

- Add a real 404 route for Cloudflare Pages/Astro output and verify unknown paths return HTTP 404.
- If Cloudflare Pages has SPA fallback behavior enabled outside the repo, disable it for this static site.
- Add a production smoke test for a known-missing path that asserts non-200.

### High - Production `/vision/` is live but repo has hidden it

Evidence:

- Production `/vision/` returns 200.
- Local source has `src/pages/_vision.astro`, not `src/pages/vision.astro`, and `site.ts` notes `/vision` is hidden until ready.
- Local Lighthouse desktop and mobile both fail at `/vision/index.html` with a 404.
- Production Lighthouse reports `/vision/` SEO score 0.83; canonical audit fails because the page points to the root URL.

Why it matters:

Production and source disagree about the indexable surface. A hidden/in-progress page is still reachable live, and its root canonical makes it look like a duplicate homepage rather than a finished canonical explainer.

Recommended fix:

- Decide whether `/vision/` should be public now.
- If no: remove it from production and return 404/410 or redirect intentionally.
- If yes: restore the route in source, give it a self canonical, include it in sitemap/navigation/LLM surfaces, and update Lighthouse URL lists.

### Medium - Cloudflare-managed `Content-Signal` breaks Lighthouse robots validation

Evidence:

- Live `robots.txt` includes Cloudflare-managed content before the repo-authored lines.
- Lighthouse flags line 30, `Content-Signal: search=yes,ai-train=no,use=reference`, as `Unknown directive`.
- All production Lighthouse SEO scores are capped below the 0.95 threshold because of this: most pages score 0.92.

Why it matters:

Major crawlers should ignore unknown robots directives, but this currently breaks the repo's Lighthouse SEO gate and makes every production SEO run fail.

Recommended fix:

- If Lighthouse gating matters more than Cloudflare content-signal policy, move the AI crawler policy out of `robots.txt` or disable the Cloudflare-managed injection.
- If the policy is intentional, update audit documentation/thresholding so `robots-txt` is treated as an accepted Lighthouse false positive, not an unresolved regression.
